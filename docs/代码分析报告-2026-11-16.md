## 0. 结论摘要（TL;DR）

**一句话**：这是一个完成度相当高的「壳 + 上游引擎」解耦架构——工程纪律和踩坑记录远超同类个人项目，但安全模型（无签名、无完整性校验、无鉴权）与发布纪律（无 CI、无锁文件、版本三元组漂移）是明显短板。

值得肯定的三件事：

1. **边界划得很干净**：Electron 壳、前端、桥接层、引擎四层职责分明，引擎在 `e785c80` 主动回退到上游纯净状态，所有定制只写在 `engine/gui/`——这是长期可维护的关键决策。
2. **进程生命周期是硬功夫**：单实例锁、`taskkill /T /F`、`--parent-pid` 看门狗、安装器判据与卸载器对齐，四层防护解决了「关不干净 / 重装提示正在运行」这个 Windows 打包顽疾，且有 `.workbuddy/memory/` 记录根因链。
3. **注释写的是「为什么」**：代码里大量解释踩坑原因（例如为什么不能用 `DETACHED_PROCESS`、为什么 `spawnSync` 会害死退出、为什么 `bsdtar` 不报进度就不编百分比），这在个人项目里很少见。

必须先修的六件事（详见 §6）：

1. **运行时 zip 下载零完整性校验**，解压出的 `python.exe` 直接被执行 → GitHub 账号/Release/CDN 任一环节被攻破即等同任意代码执行（`console/main.js:402-428`、`:222`）。
2. **桥接 API 无鉴权、无 CORS、不校验 Origin**，且多个写接口是「无 body 的 POST」可被任意网页 CSRF（`engine/gui/bridge.py` 全文无 middleware）。
3. **覆盖安装的 config 备份通配符 `oas*.json`** 漏掉用户自定义实例名（如 `main`），升级仍会清空用户数据（`console/build/installer.nsh:115`）。
4. **每次启动/退出都删光 `config/*.json`**，账号必须重绑、引擎调度状态天然易失，与引擎"持久调度"的设计互相抵消（`console/main.js:572`、`:703`）。
5. **版本一致性无人看守**：`package.json` 1.1.24 / bridge 自报 1.1.22 / 运行时 1.0.1 vs 打包默认 1.0.0 / 引擎 manifest 恒为 1.0.0 且 `MIN_ENGINE_VERSION` 算了不用。
6. **`OrochiMoans`（御魂·悲鸣）在配置模型里注册、在任务库里可见，但没有 `script_task.py`** → 用户一启用必然失败（`engine/tasks/OrochiMoans/` 只有 `assets.py` + `config.py`）。

## 2. 架构与进程模型

### 2.1 三层解耦（README 的承诺与代码的一致性：**成立**）

```
┌──────────────────────────────────────────────────────────────┐
│ 控制台 APP  OAS-Studio-Setup-1.1.24.exe（约 120 MB）           │
│  Electron 33 + renderer（app:// 协议，随控制台更新）            │
└───────────────┬──────────────────────────────────────────────┘
                │ app://oas/*（静态）   app://oas/api/*（代理）
                ▼
┌──────────────────────────────────────────────────────────────┐
│ 桥接层  engine/gui/bridge.py   FastAPI/uvicorn @ 127.0.0.1:22390│
│  REST + SSE；只暴露领域模型（实例/任务/计划/运行）               │
└───────────────┬──────────────────────────────────────────────┘
                │ 子进程 + 配置文件
                ▼
┌──────────────────────────────────────────────────────────────┐
│ 引擎  engine/（随安装包内置，29 MB）  module/ + tasks/          │
│  + Python 运行时（350–650 MB，首次使用下载到 %LOCALAPPDATA%）    │
└──────────────────────────────────────────────────────────────┘
```

拆分的真实动机（README 与代码一致）：运行时体积最大、更新频率最低，独立分发后日常更新只需下载约 120 MB 安装包。

### 2.2 运行期进程树（我按代码重建）

```
OAS Studio.exe（Electron 主进程，main.js）
├─ GPU/渲染/Utility 子进程（同名 exe）
└─ python.exe  runtime\python\python.exe -X utf8 -B resources\engine\gui\bridge.py --port 22390
   ├─ server_daemon.py --parent-pid <bridge>          （PID 落 log/gui/server_daemon.pid）
   │   └─ multiprocessing OCR server → zerorpc tcp://0.0.0.0:22268（默认关闭，见 §6.2）
   ├─ runner.py --config X --task Y --parent-pid <bridge>      每步骤一个，跑完即退
   └─ custom_click_runner.py --config X --plan-file … --parent-pid <bridge>
```

端口：22390 桥接、22268 OCR zerorpc、5037 adb server、7912 atx-agent、53516 DroidCast、20000–21000 minitouch。

### 2.3 一次「执行编排」的完整路径（最重要的数据流）

1. 前端 `startFlow()` → `POST /api/flows/{id}/run`（`app.js:1652`）。
2. `bridge.run_flow()`（`bridge.py:1417`）：
   - `_normalize_flow` / `_normalize_loop` / `_normalize_idle` 做参数收敛（`bridge.py:872-1005`）；
   - **`copy.deepcopy(flow["steps"])` 固定快照**，避免运行中被编辑（`bridge.py:1432`）；
   - `_JOB_LOCK` 内做两级互斥：同一编排不可并发、同一账号不可同时跑两份编排（`bridge.py:1435-1449`）；
   - 起 daemon 线程 `_worker` 跑轮次，轮次内 `_run_once` 逐步执行。
3. 每步：`_participants()` 解析参与账号与队长/队员角色（`bridge.py:898-922`）→ `_apply_step_config()` 把步骤 patch 深度合并进实例 config，并处理三件脏活：百鬼夜行截图/点击方式回写保护、`bondling_check` 遗留段迁移、队长端按游戏昵称回填邀请名单（`bridge.py:1354-1414`）→ `_spawn_run()` 拉子进程。
4. `_spawn_run()`（`bridge.py:1728`）：写 run 记录、`subprocess.Popen`、daemon 线程 `_pump` 逐行读 stdout → 落 `log/gui/<run_id>_<inst>_<task>.log` + 进 `deque(maxlen=4000)`，命中 `=== RESULT:` 记录成功与否。
5. runner 子进程（`runner.py:43-88`）：解析任务名 → `watch_parent` → `Script(config).run(task)` → 打印 `=== RESULT: True|False ===`。
6. `Script.run()`（`engine/script.py:540`）**绕过调度器**，直接 `load_module(tasks/<Command>/script_task.py)` 并 `ScriptTask(...).run()`，靠 `TaskEnd` 收敛成功。
7. 前端 1.5 s 轮询 `/api/jobs` 拿状态（`app.js:1681`），日志坞按 run id 增量拉 `/api/runs/{id}?offset=N`（`app.js:1869`）；单条日志抽屉走 SSE `/api/runs/{id}/stream`（`app.js:2506`）。

**这条链路的设计质量高于预期**：快照、两级互斥、取消信号分片 sleep（`_maybe_idle`、`_wait_interval` 都可秒级响应「停止」）、日志增量 offset、`deque` 上限、`rounds` 只保留最近 50 轮，都是踩过坑才会写的细节。

## 3. 模块逐一分析

### 3.1 `console/main.js`（734 行，Electron 主进程）

职责：单实例锁 → 运行时迁移/校验 → 引擎校验 → 拉桥接 → 注册 `app://` 协议 → 窗口 → 退出清扫。

**做得好的**：

- **单实例锁拿不到就 `app.exit(0)`**（`:35-38`），并注释解释了为什么不能用 `app.quit()`（异步，会继续执行到 `whenReady`，留下无窗口僵尸，安装器按 exe 路径判定"正在运行"→ 重装永远失败）。这是真实根因级修复。
- **孤儿桥接收养**：`ensureBridge()` 若发现端口上已有 bridge 且 `info.root` 与当前引擎目录一致，记下 pid 退出时回收（`:239-256`），避免"上次崩溃 → 重装提示正在运行"。
- **`app://` 协议统一入口**：静态资源 + `/api/*` 反向代理，前端因此能同源 `fetch` 与 `EventSource`，不需要 CORS。
- **`openExternalSafe()` 只放行 http/https**（`:351-358`），注释说明空串/相对路径在 Win11 会被交给 ShellExecute 弹商店。
- **诚实进度**：`bsdtar` 不吐百分比就只报耗时，不编造进度（`:434-472`）。
- **退出清扫 `sweepInstallDir()`**（`:657-675`）：用与安装器**完全相同的判据**（exe 路径前缀）杀掉自己目录下的兄弟进程，让安装器看不到残留。

**问题**：

| 严重度 | 问题 | 证据 |
|---|---|---|
| 高 | 运行时下载无 SHA-256/签名校验，`extractRuntime` 只校验 `python/python.exe` 存在，随后直接执行 | `:402-428`、`:459-463`、`:222` |
| 高 | `download-runtime` IPC 接受渲染层传入的任意 URL，向导也提供「镜像地址」输入框 → 合法功能即 RCE 入口 | `:484-486`、`wizard.html:77` |
| 中 | `MIN_ENGINE_VERSION` 与 `versionOk` 计算后**未参与门禁**（`ready = bridge && python`） | `:19`、`:138`、`:582` |
| 中 | `resetSession()` 每次启动和退出都删除 `config/*.json`（只保留 `template.json`、`gui_*`） | `:680-697`、`:572`、`:703` |
| 中 | 引擎 config 写在**安装目录内**（`resources\engine\config`），靠 `perMachine:false` 装到 `%LOCALAPPDATA%\Programs` 才可写；一旦用户改安装路径到受保护位置即失败 | `package.json:58`、`main.js:59-66` |
| 低 | `app://` 静态路径校验用 `file.startsWith(RENDERER_DIR)`（无分隔符），`rendererX` 这类同前缀目录可绕过；当前无可利用目录 | `:306-309` |
| 低 | 全局无 CSP（主窗口与向导都没有），`el({html})` 是唯一的 `innerHTML` 旁路 | `index.html`、`main.js` |

### 3.2 `console/preload.js`（24 行）

极小暴露面，`contextIsolation: true` + `sandbox: true` + `nodeIntegration: false`（`main.js:344`），只暴露 `runtime.*`、`wizard.done`、`onBridgeDown`。**这是正确的写法**，值得肯定。

### 3.3 `console/renderer/app.js`（2799 行单文件 SPA）

形态：IIFE + 严格模式，`el()` hyperscript + `esc()` + 全量重绘 + hash 路由；状态是单个 `state` 对象；持久化只在 `localStorage` 存 3 个 UI 偏好（日志坞开合/高度/自动滚动），业务数据全在服务端 config。

**5 个视图**：总览（账号与模拟器）/ 任务编排 / 执行记录 / 已知问题 / 高级设置。

**最有特色的实现**：`dockAnnotate()`（`:1745-1775`）用 18 条正则把引擎英文日志翻译成 `▸` 开头的中文节点注释（`Page arrived page_town` → 经 `PAGE_CN` 字典 → 「已进入「町中」」），并把连续重复注释去重。这是把"日志可读性"当成产品功能在做。

**问题**（前面三条我逐行核对过）：

1. **已知问题排序反了**：`const order = { error: 0, warn: 1, info: 2 }` 后用 `(order[a.severity] || 9)`，`error` 的 `0` 是 falsy → 变成 9，**最严重的排到最后**（`:2535-2536`）。
2. **总览/执行记录每 5 秒被弹回顶部**：`:205` 对非 `flows` 视图无条件 `scrollTop = 0`，而 `:2775-2783` 每 5 s 对 `overview`/`runs` 全量 `render()`，`.view` 正是滚动容器（`app.css:153`）。
3. **`loadCatalog(force)` 的 force 分支永不可达**（`refreshAll` 不传参）→ "刷新数据"按钮永远不刷新 catalog，后端增删任务/issue 后必须重启窗口（`:232-236`、`:290`）。
4. **自定义点击方案编辑会静默丢字段**：`ccDraft`/`ccPayload` 无条件把 `forbid` 覆盖为 `[]`、`ocr_roi` 覆盖为全屏（`:1057-1058`、`:1078-1079`）。
5. **组队步骤永远拿不到状态徽章**：`teamStepRow` 没设 `data-step`（`stepRow` 有），`applyJobStatus` 因此 `return`（`:821`、`:880`、`:1710-1712`）。
6. **两套日志通道实现重复且能力不一致**：日志坞有中文注释/账号前缀/2400 行上限，SSE 抽屉逐字复制了着色逻辑但**没有**这些能力，且抽屉的自动滚动读的是日志坞的设置（`:2522-2530` vs `:1847-1858`）。
7. **错误处理粒度不稳**：`api()` 丢弃 HTTP 状态码 → 409 只能靠中文字符串 `/正在执行|执行中/` 识别，后端改一个字 UI 就退化（`:74-77`、`:1667-1672`）；`deleteFlow`/`stepDelete` 的 `await api()` 无 catch；`watchJobs` 的 catch 直接 `clearInterval` 且不提示（桥接抖动一次日志坞静默停更）。
8. **超长函数**：`openCustomClickEditor` 188 行、`openStepConfig` 126 行、`openBindDrawer` 95 行。
9. **无键盘可达性**：全文无 `keydown`/`Escape`，抽屉与模态不能 Esc 关闭、无焦点捕获、无 `:focus-visible` 样式。
10. CSS 变量 `--muted` 在 `app.css:517`/`:520` 被使用但 `:root` 从未定义（颜色回退为继承值）。

**XSS 面评估：低**。23 处 `innerHTML` 全部是静态字符串（图标 SVG、表头常量），所有服务端/用户数据一律走 `text: …`（`textContent`）。但这靠约定而非机制——`el()` 的 `html` 属性是常开的旁路。

### 3.4 `engine/gui/bridge.py`（1944 行，自研核心）

REST 面 34 个端点，覆盖：元数据（catalog/schema/version/health）、设备、账号资料、实例 CRUD、任务配置、编排 CRUD、方案库、自定义点击、执行（runs/jobs/SSE）。

**值得肯定的设计**：

- **`_instance_path()` 拒绝含 `/`、`\`、前导 `.` 的实例名**（`:149-155`），路径穿越挡住了。
- **`_save()` 原子写**：`tmp` + 备份 `.bak` + `tmp.replace()`（`:166-172`）。
- **编排快照 + 两级互斥 + 运行中禁止删账号**（`delete_instance` 先 terminate 再删配置，`:690-732`）。
- **`_task_schema()` 用子进程内省 pydantic 模型**（`_PROBE`，`:449-500`）：用独立进程隔离导入副作用（引擎 `module/logger.py:59` 在 import 时 `os.chdir`！），结果落 `.cache/schema.json`。这个思路是对的。
- **自定义点击执行器复用引擎既有能力**（`Device`/`BaseCor`/正态随机落点/防封休眠），不另造随机算法（`custom_click_runner.py:1-18`），并在长循环里 `device.disable_stuck_detection()` 避免引擎 60 s 卡死误判（`:46`）。

**问题**：

| 严重度 | 问题 | 证据 |
|---|---|---|
| 高 | **无任何鉴权、CORS、Origin 校验**。`POST /api/instances/unbind-all`、`/api/flows/{id}/run`、`/api/runs/{id}/stop`、`/api/jobs/{id}/stop` 都是无 body 或可选 body → 属「简单请求」，恶意网页无需预检即可触发 | 全文无 middleware；`:735`、`:1417`、`:1652`、`:1872` |
| 中 | schema 缓存**永不失效**：引擎更新后表单仍是旧 schema，只能手工删 `.cache/schema.json` | `:440-500` |
| 中 | `_RUNS` / `_JOBS` 永不回收，`log/gui/*.log` 永不清理（一次会话跑几十个任务即累积上百 MB） | `:1758-1772`、`:1450`、`:1775` |
| 中 | `_RUNS` 的结构性写入有锁，但 `run["lines"]`/`run["status"]` 跨线程读写无锁（`_pump` 写、`get_run`/`stream_run` 读），依赖 deque/GIL 侥幸正确 | `:1774-1794`、`:1858-1912` |
| 低 | SSE 用 `time.sleep(0.6)` 轮询生成器，每个连接占一个线程；无心跳、无断线清理 | `:1895-1912` |
| 低 | `/api/version` 硬编码 `1.1.22`，与 `package.json` 的 1.1.24 漂移 —— 这个端点的用途恰恰是「确认用户跑的是哪份 bridge」，硬编码使其失效 | `:586-589` |
| 低 | `_i18n()` 用可变全局 `_I18N` 做懒加载，无锁 | `:503-514` |

### 3.5 `engine/gui/` 其余 4 个文件

- **`runner.py`（92 行）**：薄封装，`resolve_task()` 忽略大小写/下划线把配置键映射到目录名（`:27-40`）；`SystemExit` 分支把 `exit(1)` 判失败、`None/0` 判成功（`:79-85`）——细节正确。
- **`proc_guard.py`（110 行）**：`OpenProcess(0x00100000)` + `WaitForSingleObject` 探活，父进程消失即 `taskkill /T /F` 自杀。**这是全项目最扎实的一段代码**，注释里写清了背景：Electron `TerminateProcess` 不走 atexit，所以 bridge 里的清理从未生效过。
- **`server_daemon.py`（59 行）**：意图是保活 OCR 服务、省掉每步 6 s 预热。**但实际空转**：`ensure_ocr_server_started()` 第一行判 `deploy_config.StartOcrServer`，而默认值是 `False`（`engine/deploy/config.py:38`）→ 直接 return，守护进程只 sleep。`UseOcrServer` 同样默认 `False`（`:37`），所以发行形态下每个 runner 子进程各自加载 ONNX 模型——注释里想解决的性能问题依然存在（推测，取决于用户 `config/deploy.yaml`，而该文件被打包排除、由 `DeployConfig.__init__` 运行时生成）。
- **`custom_click_runner.py`（517 行）**：控制台「自定义点击」的运行时，抓图 → OCR 文字条件 → 矩形内正态随机点击 → 层间跳转 / 重复 / 超时 / 自动接管战斗。属于产品差异化功能，代码质量尚可。

### 3.6 `engine/gui/catalog.py`（634 行）

纯数据层：任务中文名、游戏内分类（探索觉醒/御魂契灵/组队副本/逢魔之时/结界阴阳寮/活动/商店/其他）、玩法说明、是否支持组队、已知问题、字段提示。**不 import 引擎任何代码**（`:4-11` 明确写了这条原则），保证 UI 与执行彻底解耦。分类按游戏庭院底部菜单对齐，这个产品判断是对的。

风险：它是**手写维护的镜像**，上游任务增删不会自动同步 → 与 `config_model.py` 的 57 个字段、`tasks/` 的 61 个目录之间靠人工保持一致。

### 3.7 引擎内核（`engine/module`、`engine/tasks`，上游派生）

- **任务注册不是插件化**：`module/config/config_model.py:4-84` 手写 57 个 import，`:86-156` 逐字段声明 pydantic 模型；新增任务要改 4 处（目录、config_model、config_manual 优先级、config_menu 分组）。唯一的目录扫描是 `tasks/GameUi/registry.py:70-91`（页面导航图），与调度无关。
- **`Script.run()` 绕开调度器**（`script.py:540-574`）：控制台一任务一进程直调，`Script.loop()`（`:630-747`，含优先级/FIFO/失败 3 次退出/防封作息）在发行形态下形同虚设。
- **双设备通路**：ADB 模拟器（`device.py`，8 种截图方式 + `auto` 基准测试自适应）与 Windows 桌面客户端（`desktop_impl.py` 77 KB，DC BitBlt 截图 + `SendMessage` 点击，要求窗口不可最小化、显示器常亮、1280×720）。
- **识别栈**：ppocr-onnx（PaddleOCR 的 ONNX 移植，`onnxruntime`）+ OpenCV `TM_CCOEFF_NORMED` 模板匹配（含掩码匹配、多尺度、NMS、SIFT+FLANN、亮度/饱和度启发式）；资产由 `dev_tools/assets_extract.py` 从 JSON 生成成 `assets.py` 常量（生成物，不可手改）。
- **配置模型**：每账号一个整份 JSON，pydantic v2 全量校验，`__setattr__` 每次赋值都全量回写（`config_model.py:170-179`）；**无 schema 迁移**（`config_updater.py:19-35` 是 `pass` 桩）→ 旧 JSON 会累积死键。
- **确认的缺陷**：`OrochiMoans` 有配置无实现（61 个任务目录里 `General`/`GlobalGame`/`Script` 是框架目录，**只有 `OrochiMoans` 是"有 config.py 无 script_task.py"**）；`tasks/` 里 `mvp`/`AbyssShadows` 等标注来源 `roarhill/oas`、`TripleEarth`，GPL 义务需保留署名；`module/ocr/rpc.py:59,116` bind `0.0.0.0` 且 `pickle.loads` 远端字节（默认关闭）。

## 4. 设计亮点（值得学习）

1. **四层进程清理**，每一层都对应一个真实故障：`requestSingleInstanceLock`（重复双击→僵尸）→ `taskkill /T /F` 异步 + `unref`（`spawnSync` 阻塞主线程→窗口消失进程还在）→ `--parent-pid` 看门狗（`TerminateProcess` 不走 atexit→OCR 孤儿）→ 安装器判据与卸载器对齐（桥接 python 在 `%LOCALAPPDATA%`，默认判据看不见）。
2. **引擎纯净策略**：`e785c80` 把自研识别逻辑全部撤回，只在 `gui/` 壳层做编排。这让每次同步上游（`76c20b3`、`ba80668`）的成本趋近于零。
3. **编排运行时的健壮性**：deepcopy 快照、账号级互斥、取消信号可秒级响应、日志增量 offset、`rounds` 只留 50 轮、`deque(maxlen=4000)`。
4. **业务知识的沉淀**：`catalog.py` 把"哪个玩法支持双账号组队"编码成 `TEAM_TASKS`，`_participants()` 按「组队步骤 > 步骤 participants > 全部账号」三级降级，`_apply_step_config()` 甚至处理了历史错误的 `bondling_check` 段迁移。
5. **诚实的产品表达**：`bsdtar` 不报百分比就只报耗时；随机发呆的剩余秒数显示在日志坞标题；409 冲突时前端自动挂到正在跑的作业上。

### 9.3 重复模拟器（`emulator-XXXX` 与 `127.0.0.1:PORT`）

**根因**：同一台安卓实例会以两个传输名同时出现在 `adb devices` 里——MuMu 12 通过模拟器本地控制台端口暴露 `emulator-5554`，又通过多开 adb 端口暴露 `127.0.0.1:16384`。`_device_detail()` 把每一行都当成一台独立设备，只按 serial 判断绑定关系，于是已绑定的 `127.0.0.1:16384` 与「同一台」的 `emulator-5554` 被当成两台 → 多出一条未绑定设备。

**改动**（`engine/gui/bridge.py`）：

1. 新增 `_PROBE_SHELL` / `_probe_device()`：一次 `adb shell` 往返（原来要 3 次）取齐 `boot_id` / `ro.product.model` / `ro.serialno` / `wm size` / `wm density`，用 `_OAS_*` 标记分段解析。
2. `_device_detail()` 按 `boot_id`（内核每次启动生成的 UUID，与传输方式无关）分组；取不到退 `ro.serialno`，再退 serial（不合并）。
3. 组内保留优先级：**已绑定 serial** > `127.0.0.1:*` > 其它 > `emulator-*`；被合并掉的写入 `aliases`。这样实例卡片按 `inst.serial` 找设备仍然命中。
4. 顺带：设备探测从 3 次 `adb` 调用降为 1 次，`/api/devices` 更快。

**验证**：用桩数据跑了 5 组用例（绑定 TCP / 绑定 emulator / 两台真不同 / 探测失败 / 只有 serialno），合并与保留优先级均正确；探测失败时不误合并。
